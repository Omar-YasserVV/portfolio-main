The browser isn't just a rendering engine — it's a security gatekeeper. It enforces default boundaries that protect users from common attacks — but only if developers know how to use them.

In this article, we'll walk through some of the most essential and battle-tested web security practices — no fluff, just what actually matters.

## Use **HttpOnly**, **Secure**, and Smart Token Storage

When dealing with **sensitive tokens** like **access tokens** or **refresh tokens**, how and where you **store them** is just as important as how you generate and use them.

### Recommended Cookie Flags

- **HttpOnly**: Prevents JavaScript from accessing the cookie via `document.cookie`, protecting against **XSS attacks**.
- **Secure**: Ensures the cookie is only sent over **HTTPS** connections.
- **SameSite**: Helps prevent **CSRF attacks**. Use `SameSite-Strict` or `Lax` where possible.

### Storage Options

Access tokens in memory (e.g., JavaScript variables) are secure but they vanish on page refresh. Refresh tokens should always be stored in **HttpOnly** cookies.

```javascript
// Express example
app.use(
  cors({
    origin: "https://yourfrontend.com",
    credentials: true,
  })
);
```

## Bonus: Protect with CORS

CORS (Cross-Origin Resource Sharing) is your backend's way of saying who can talk to it and what's allowed.

Set rules that match your front-end origin:

```http
Access-Control-Allow-Origin: https://yourfrontend.com
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
```

### If you're using cookies for auth, don't forget:

```javascript
// Express example
app.use(
  cors({
    origin: "https://yourfrontend.com",
    credentials: true,
  })
);
```

**Important:** For cookies to work across origins, you need both `credentials: true` on the client and `Access-Control-Allow-Credentials: true` on the server.
